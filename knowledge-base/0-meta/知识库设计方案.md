## 一、背景与目标

### 1.1 背景

当前技术资产主要集中在博客项目的 `source/_posts/` 目录下：19 篇 Markdown 文章，覆盖测试理论、混沌工程、自动化测试、云原生、Linux、网络、Python、DevOps 工具等。

这些文章存在标题泛化、通用知识与项目细节混杂、缺少测试视角、图片与文章文件夹分散等问题，难以直接作为结构化知识库复用。本次重构先将博客存量文章迁移到本地 `knowledge-base/`，形成可沉淀、可检索、可复用的专业测试开发知识库。

### 1.2 目标

1. **知识管理**：建立分类清晰的专业知识库，让博客存量内容可检索、可复用。
2. **可持续沉淀**：形成命名规范、标签体系、更新机制，支撑长期积累。
3. **AI 能力构建**：把快速发展的 AI 知识按应用场景落地到测试开发各环节。
4. **职业资产**：让知识库成为简历素材库，能反向梳理个人优势与项目成果。

**本次范围**：第一步仅迁移博客项目 `source/_posts/` 中的 19 篇存量文章，暂不处理飞书文档。

## 二、设计原则

### 2.1 目录按领域聚合，不按来源拆分

不建议按"通用知识"与"项目实战"拆成两套平级目录。原因：

- 同一主题的两套文档会造成内容重复与更新不同步。
- 检索时通常按问题域检索（如"K8s 调度异常"），而非按来源检索。
- 项目黑话和版本号会让文档快速失效，半年后连自己都难读懂。

**正确做法**：按"领域/主题"聚合内容，通过标签体系区分知识属性。

### 2.2 知识双轴模型

- **横轴（目录）**：按测试开发专业领域组织，保证知识的完整性和可检索性。
- **纵轴（文档类型）**：通过标签区分理论、实战、项目、复盘、规范、速查等类型。

### 2.3 每篇文档必须回答三个问题

1. 这个知识对测试开发工作有什么用？
2. 测试切入点在哪里？
3. 有哪些可复用的模板/脚本/Checklist？

### 2.4 AI 知识分层沉淀

AI 发展快，不要每出一个新模型就写一篇文档：

| 层级 | 更新频率 | 整理方式 |
|---|---|---|
| 趋势层 | 每月 | 只记一句话结论和链接 |
| 方法层 | 每季度 | 沉淀可迁移的方法论 |
| 资产层 | 每半年 | 形成可复用的模板/脚本 |

## 六、通用知识与项目实战的整理方法

### 6.1 不建议拆两套目录

按"通用知识 vs 项目实战"拆两套目录容易出现：

- 重复片段不可避免
- 更新时容易遗漏
- 检索路径混乱
- 项目经验被项目黑话"绑架"
- 知识难以横向迁移复用

### 6.2 推荐做法：领域聚合 + 类型区分 + 项目索引

```text
领域目录（主目录）        项目索引页（辅助入口）
      │                        │
 5.2 容器/K8s    ←────    项目：CCE
 ├── 理论                      ├── 节点调度测试
 ├── 实战                      ├── 存储挂载测试
 └── 复盘                      └── 相关领域链接
```

- **主目录按领域分**：通用知识和项目经验都放进去
- **项目索引页作为横向视图**：只放链接，不放重复内容
- **项目标签串联**：如 `#CCE`、`#EVS`，一键过滤项目相关文档

### 6.3 文档类型标签规范

文档类型不再通过标题前缀体现，而是通过**标签**识别。在整理文档时，根据内容选择对应标签：

| 标签 | 含义 | 示例 |
|---|---|---|
| `#理论` | 概念、原理、方法论 | `#理论` Kubernetes 核心概念 |
| `#实战` | 通用技术实践 | `#实战` kubeadm 部署 K8s 集群 |
| `#项目` | 来自具体业务项目 | `#项目` 云容器引擎 CCE 测试实践 |
| `#复盘` | 问题排查、故障复盘 | `#复盘` CCE 节点调度异常根因分析 |
| `#规范` | 团队规范、Checklist | `#规范` CCE 自动化用例设计规范 |
| `#速查` | 命令、配置、快捷参考 | `#速查` kubectl 常用命令 |

> 注：标题保持简洁，仅使用 `编号 + 主题名`，类型信息通过标签表达。

### 6.4 项目实战文档模板

```markdown
# 一、项目背景
- 产品：xxx
- 测试目标：xxx
- 涉及版本：xxx

# 二、核心知识点关联
- 关联理论：[目录链接]
- 关联工具：[目录链接]

# 三、测试场景设计
| 场景 | 输入 | 预期 | 实际结果 | 状态 |

# 四、遇到的问题与复盘
- 问题、根因、解决、沉淀

# 五、可复用资产
- 测试脚本、配置模板、排查 Checklist

# 六、后续待办
```

## 八、为简历服务的知识库设计

### 8.1 知识库即简历素材库

每个项目实战文档都要能回答简历上的四个问题：

1. **你做了什么？**（职责）
2. **解决了什么业务问题？**（价值）
3. **用了什么技术和方法？**（技术栈）
4. **取得了什么可量化结果？**（成果）

### 8.2 项目素材示例：AI 失败归因

| 简历四问 | 知识库沉淀 |
|---|---|
| 做了什么 | 设计并实现 AI 智能失败归因系统 |
| 解决什么问题 | CI 失败后人工逐条查看 Allure 报告效率低、同类失败重复分析 |
| 技术方法 | pytest + Allure + LLM + 失败聚类 + IM 通知 |
| 量化成果 | 失败分析耗时从 30 分钟/次降至 5 分钟/次；聚类准确率达到 xx% |

### 8.3 用项目证明自己，而不是堆砌工具

❌ 不佳：熟练使用 Claude Code  
✅ 更好：在 CCE UI 自动化项目中引入 Claude Code，基于 Codex 实现自修复式脚本开发，将新需求脚本开发周期从 2 人日缩短至 0.5 人日，脚本稳定性从 85% 提升至 96%。

## 九、本地知识库落地规范

### 9.1 命名规范

- 页面标题：`[编号] 主题名`
- 文件名：`[编号] 主题名.md`
- 示例：`5.1.1 云服务器 ECS 功能与测试策略.md`
- 编号规则：按目录层级顺序编号，如 `01`、`1.1`、`1.1.1`
- 避免使用"学习笔记""总结""分享"等泛化词
- 文档摘要必填：1-2 句话说明解决什么问题

> 注：标题和文件名使用 `编号 + 主题名`，类型信息通过标签表达。

### 9.2 文档类型识别

不再通过标题前缀区分文档类型，而是通过**标签体系**和**摘要**来体现。常用文档类型标签：

| 标签 | 含义 | 示例 |
|---|---|---|
| `#理论` | 概念、原理、方法论 | `#理论` 软件质量模型 |

## 十二、总结

本方案的核心思想是：

1. **按领域聚合，不按来源拆分**：通用知识和项目经验放在同一目录下，通过类型标签区分。
2. **AI 能力拆散落地**：把 AI 按应用场景分配到测试开发各环节，同时用横向入口页系统学习。
3. **知识库服务职业发展**：每篇项目文档都要能回答简历四问，让知识库成为个人技术资产和简历素材库。
4. **可持续沉淀**：通过命名规范、标签体系、模板和定期 Review 机制，保证知识库长期有效。
5. **项目视角横向串联**：通过项目索引页把散落在不同领域的项目知识关联起来，既避免重复，又方便回溯。
