# 03\.框架架构整体分析

# 基于当前项目的自动化测试框架架构分析与优秀标准定义

> 本文基于 `playwright-sugon` 项目真实代码结构，从测试架构师视角分析如何打造优秀的自动化测试框架。

> 适用对象：测试开发团队、技术负责人、架构师

---

## 一、优秀自动化测试框架的评判标准

优秀不是"能跑起来"，而是在**规模化、长期化、团队化**场景下依然保持健康。

### 1\.1 七大核心评判维度

|维度|权重|定义|参考量化指标|
|---|---|---|---|
|**可维护性**<br>|⭐⭐⭐⭐⭐|需求变更时，修改成本低、影响范围可控|单需求变更平均修改文件数 ≤ 3；Page Object 类平均行数 ≤ 300|
|**可扩展性**|⭐⭐⭐⭐⭐|新增服务/功能时，无需破坏既有结构|新增服务测试所需新建文件数 ≤ 4（Page \+ Fixture \+ Helper \+ Test）|
|**稳定性**|⭐⭐⭐⭐⭐|用例失败率中真实 Bug 占比高，环境抖动误报率低|flaky 率 ≤ 5%；同一用例连续 10 次执行通过率 ≥ 95%|
|**执行效率**|⭐⭐⭐⭐|反馈周期短，资源消耗合理|核心流程执行时间 ≤ 30 分钟；并行度可弹性伸缩|
|**可观测性**|⭐⭐⭐⭐|失败时可快速定位根因，报告对非技术人员友好|失败用例平均定位时间 ≤ 10 分钟；报告包含 UI 截图\+日志\+SSH 输出|
|**易用性**|⭐⭐⭐|新成员上手成本低，API 设计符合直觉|新成员独立编写首个用例时间 ≤ 2 天；公共方法命名零歧义|
|**环境适应性**|⭐⭐⭐|一套代码可适配多环境，无需分支维护|环境切换仅需改配置，无需改代码|

### 1\.2 成熟度分级

|等级|要求|说明|
|---|---|---|
|**及格**|满足维度 1\-3|框架可用，能发现问题|
|**良好**|满足维度 1\-5|框架好用，团队愿意用|
|**优秀**|七维度全部满足|框架成为生产力倍增器|

> ⚠️ **关于量化指标的说明**：上表中的具体数字（如 ≤ 300 行、≤ 5% flaky 率）是基于行业经验值和本项目语境推导的**参考值**，而非来自某个权威标准的硬性规定。详见文末「信息源说明」部分。

## 三、逐层诊断：现状 vs 优秀标准的差距

### 3\.1 配置/数据层（`config/`）

**现状评分：⭐⭐⭐⭐（良好）**

|优点|问题|
|---|---|
|三层配置合并（base → env → CLI）设计合理|`env.yaml` 中环境配置与代码耦合，新增环境需改文件|
|`Config.get()` 全局访问接口统一|缺乏配置 Schema 校验，错误配置延迟到运行时才发现|
|`constants.py` 统一管理常量|密码等敏感信息明文存储在 YAML 中|

**→ 优秀的改进方向：**

```Python
# 1. 引入配置 Schema 校验（Pydantic）
class EnvConfig(BaseModel):
    host: IPv4Address
    username: str
    password: SecretStr  # 敏感信息加密存储
    browser: Literal["chromium", "firefox", "webkit"]
    stor: str

# 2. 环境配置外置到环境变量或 Vault
# 避免 env.yaml 入库，支持 CI/CD 动态注入

```

---

### 3\.2 公共/基础设施层（`common/`）

**现状评分：⭐⭐⭐⭐（良好）**

**优点：**

- `BasePage` 聚合 9 个 Mixin，组件化程度高

- `CustomLocator` 封装了日志和重试能力

- SSH 三层封装（`SSHClientBase` → `ScliMixin`/`CloudOpsMixin` → `SSH`）设计优雅

**问题：**

|问题|影响|
|---|---|
|`common/mixins/` 目录为空，所有 Mixin 都塞在 `components/` 里|组件 vs Mixin 职责边界模糊|
|`Playwright` 类直接包装 `page.locator()`，未做等待策略兜底|部分用例因元素未就绪而 flaky|
|缺少**全局异常拦截和自动恢复机制**|测试失败时只能依赖 pytest hook，无法在框架层做智能重试|

**→ 优秀的改进方向：**

```Python
# 统一等待策略封装
class CustomLocator:
    def click(self, timeout=10000, auto_retry=True):
        """点击操作内置智能重试和等待"""
        try:
            self._locator.click(timeout=timeout)
        except TimeoutError as e:
            if auto_retry and self._is_overlay_blocking():
                self._dismiss_blocking_element()
                self._locator.click(timeout=timeout//2)
            else:
                raise

```

### 3\.3 工具层（`utils/`）

**现状评分：⭐⭐⭐（及格）**

**问题：**

|问题|影响|
|---|---|
|`util.py` 是"大杂烩"文件（1\.4 万行），包含随机数据、文件查找、YAML 加载、装饰器等|工具间耦合，难以单独测试和维护|

#### 问题：EVS 模块定位器依赖正则匹配中文文本

```Python
# pages/storage/evs.py（当前实现）
```

- `_xxx_fixtures.py` 放单一业务域、跨文件复用的 fixture

- `_xxx_helpers.py` 放不具备 fixture 生命周期语义的纯函数

#### 优点 2：跨模块 Fixture 复用机制成熟

```Python
# testcase/compute/conftest.py
from sugon_web.testcase.network.conftest import (
    _create_security_groups,
    _cleanup_security_groups,
)

@pytest.fixture(scope="function")
def sg(browser_context, config, request):
    """compute 模块复用 network 模块的安全组创建/清理逻辑"""
    page = _create_logged_in_page(browser_context, config)
    vpc_page = VpcPage(page)
    count = getattr(request, "param", 1)
    names = _create_security_groups(vpc_page, count)
    yield names[0] if count == 1 else names
    try:
        _cleanup_security_groups(vpc_page, names)
    finally:
        page.close()

```

**价值：** 避免了跨模块重复实现安全组创建逻辑，保证了清理行为的一致性。

#### 优点 3：`image` fixture 支持动态参数化

```Python
# testcase/compute/conftest.py
@pytest.fixture()
def image(ssh_host, ecs_page, request):
    """动态创建镜像，支持从测试用例层传参。"""
    params = getattr(request, "param", {})
    name = params.get("name", random_data())
    backend = params.get("backend", ecs_page.storage_pool)
    image_name = params.get("image", "AnolisOS-8.9-x86_64-minimal.iso")
```

#### 问题：`bms_instance` fixture 越界包含断言和场景编排

```Python
# testcase/compute/conftest.py:106-160
def bms_instance(bms_page, vm):
    def _create(name="bms-0430", ...):
        # ... 场景编排 ...
        assert bms_page.get_row_data(name) is not None    # ← Fixture 里写了断言
        for waited in range(0, 1800, 30):
            # ... 复杂等待循环 ...
        return name
    return _create

```

**问题：**

- **断言**按规范应在 Test Class 中，不应出现在 Fixture

- **场景编排**（1800 秒轮询等待运行中）按规范应在 Page Object 或 Test Class 中

**→ 优秀的改进方向：**

```Python
# 1. 将断言移回测试类
def test_bms_create(self, bms_instance):
    name = bms_instance(name="bms-test")
    assert bms_page.get_row_data(name) is not None  # 断言在测试类中

# 2. 将等待逻辑下沉到 Page Object
class BmsPage(BasePage):
    def wait_for_running(self, name, timeout=1800):
        """等待裸金属实例变为运行中，返回实际等待时长"""
        for waited in range(0, timeout, 30):
            rd = self.get_row_data(name)
            if rd and "运行中" in rd.get("状态", ""):
                return waited
            time.sleep(30)
        raise TimeoutError(f"实例 {name} 未在 {timeout}s 内变为运行中")

```

#### 优点 1：ECS Helper 封装了标签生命周期

```Python
# testcase/compute/_ecs_helpers.py
def create_labels(ecs_page, *, count=1):
    """批量创建标签并返回实际标签名列表。"""
    label_names = []
    for _ in range(count):
        name = f"label-{random_data()}"
        label_name = ecs_page.create_label(name)
        ecs_page.assert_popup_success("新建标签成功")
        label_names.append(label_name)
    return label_names


def delete_labels(ecs_page, label_names):
    """批量删除标签，供标签类 fixture 统一清理使用。"""
    if not label_names:
        return
    ecs_page.goto_service("弹性云服务器")
    ecs_page.goto_submenu("标签")
    ecs_page.batch_delete_label(label_names)

```

**价值：** `create_labels` 和 `delete_labels` 配对设计，被 `_ecs_fixtures.py` 中的 `labels` fixture 消费，形成了完整的"创建\-使用\-清理"闭环。

#### 优点 2：Network Helper 实现了环境组装逻辑

```Python
# testcase/network/_acl_helpers.py
def build_acl_env(acl_name, vpc_data, vm_data):
    """组装 ACL 测试场景所需的环境数据。"""
    vm_list = _normalize_acl_vm_list(vm_data)
```

#### 改进空间：引入 Builder 模式管理 ECS 创建参数

当前 ECS 创建参数直接在 fixture 或测试方法中拼装，结构复杂时容易遗漏字段：

```Python
# 当前做法：分散拼装
create_kwargs = {
    "name": f"ecs-{random_data()}",
    "count": 1,
    "cluster": "Autotest",
    "flavor": {"cpu": 4, "memory": 8},
    "storage_pool": "xstor-test",
    ...
}

```

**→ 优秀的改进方向：**

```Python
# helpers/builders.py
class EcsCreateBuilder:
    def __init__(self):
        self._data = {
            "count": 1,
            "cluster": "Autotest",
            "login_type": "密码",
        }
    
    def with_name(self, name: str):
        self._data["name"] = name
        return self
    
    def with_flavor(self, cpu: int, memory: int):
        self._data["flavor"] = {"cpu": cpu, "memory": memory}
        return self
    
    def with_data_disk(self, size: int, vol_type: str = "xbd-type"):
        disks = self._data.get("data_disks", [])
        disks.append({"size": str(size), "vol_type": vol_type, "count": "1"})
        self._data["data_disks"] = disks
        return self
    
    def build(self):
        return self._data.copy()

# 使用
params = EcsCreateBuilder()\
    .with_name(f"ecs-{random_data()}")\
    .with_flavor(4, 8)\
    .with_data_disk(100)\
    .build()
ecs_page.ecs_create(**params)

```

### 6\.2 各指标的溯源依据

#### "Page Object 类平均行数 ≤ 300"

- 理论基础：Robert C\. Martin《Clean Code》单一职责原则（SRP）

- 数值推导：当前项目 SLB 拆分后的文件多在 100\-250 行；一个屏幕可展示 50\-80 行，300 行 ≈ 4\-6 屏，是认知负荷的合理上限

#### "flaky 率 ≤ 5%"

- 理论基础：Google《Software Engineering at Google》（O'Reilly, 2020）第 11 章

- 数值推导：\> 10% 时测试 suite 失去信任；5\-10% 需持续关注；\< 5% 为可控区间

#### "核心流程 ≤ 30 分钟"

- 理论基础：Martin Fowler《Continuous Integration》中"集成构建应在 10 分钟内完成"（单元测试级别）

- 数值推导：UI 自动化天然比单元测试慢，业界冒烟测试普遍接受 10\-20 分钟，核心回归 30\-60 分钟

#### "新成员上手 ≤ 2 天"

- 纯经验值，基于当前项目已有清晰 4 层规范、Allure 集成、PO 模式友好的综合判断

## 七、结论

当前项目框架处于\*\*"良好"水平\*\*，核心基础设施（配置系统、SSH 后端验证、Allure 报告、组件化 BasePage）已经搭好，且 **ECS/Network 模块在 Fixture 拆分、Helper 设计、跨模块复用方面已接近优秀标准**。

**阻碍其从"良好"跨越到"优秀"的三大瓶颈：**

1. **定位器策略偏脆弱** — EVS 等模块大量依赖 Element UI 的 CSS 类名和中文文本正则匹配，前端升级时失效风险高

2. **Fixture 边界偶发越界** — 个别 fixture（如 `bms_instance`）内部包含断言和复杂场景编排，模糊了 Fixture 与 Test Class 的职责边界

3. **工具层未按职责拆分** — `util.py` 1\.4 万行大杂烩，随机数据生成、文件查找、YAML 加载耦合在一起

修复以上三点，框架将从"能跑"迈向"好用"，最终成为团队的生产力倍增器。
