# 元素定位实践案例

## Text 定位

```Python
page.click('"登 录"')
page.click('text="登 录"')
page.get_by_text("登 录").click() 
```

- `get_by_text(text).click()`​：这是通过 Playwright 提供的语义化快捷定位器实现的。`get_by_text(text)`会生成一个 `Locator`对象（表示“按文本匹配的元素集合”），随后调用 `click()`方法触发点击。

- `click(text)`​​：这是直接通过选择器字符串定位元素。Playwright 支持在 CSS 选择器中使用 `text=`语法（非标准 CSS，是 Playwright 扩展的文本定位语法），例如 `page.click('text=提交')`。这种方式本质是将文本匹配逻辑硬编码在选择器字符串中。

## Placeholder 定位

```Python
# 两者最终都是生成一个locator对象
page.get_by_placeholder("请输入登录密码")
locator('[placeholder="请输入登录密码"]')
```

- `get_by_placeholder("...")`​：这是 Playwright 提供的语义化定位器（Semantic Locator）​​，属于高层抽象接口。它的设计目标是让代码更易读、更符合人类语言习惯（“按 placeholder 文本定位”），底层会自动将语义转换为对应的原生选择器逻辑（如 `placeholder`属性选择器）。

- `locator('[placeholder="..."]')`​：这是通过 Playwright 的 `locator()`方法直接使用原生 CSS 选择器字符串创建定位器。`[placeholder="..."]`是标准的 CSS 属性选择器，明确描述元素的 `placeholder`属性值。

# Playwright框架的常用方法

## Page类

```Shell
*page.wait_for_timeout()    # 显式等待，适用于调试*
page.wait_for_load_state()    # 等待页面达到所需的加载状态，适用于导航后需要确保页面完全加载
```

在大多数测试场景中，应该优先使用Playwright的自动等待和具体的断言，而不是依赖 wait\_for\_load\_state\(\)

## Locator类

```Shell
is_visible()    # 元素是否可见（返回布尔值，适用于条件判断）
*is_enabled()    # 元素是否可用*
locator.all()    # 返回定位器列表，适用于需要对多个元素执行不同操作的场景（不等待元素匹配、不适用于动态列表）
locator.count()    # 返回匹配元素的数量

text_content()         # 返回第一个匹配元素的文本内容
*all_text_contents()    # 返回所有匹配元素的文本内容列表*
inner_text()           # 返回第一个匹配元素的"可见"文本内容（更接近用户看到的文本）
all_inner_texts()     # 返回所有匹配元素的"可见"文本内容列表
```

**textContent 与 innerText 的区别**

textContent ：

- 获取元素的所有文本内容，包括隐藏的文本

- 不考虑CSS样式

- 性能更好

innerText ：

- 只获取用户可见的文本内容

- 考虑CSS样式（如 display: none 的元素不会包含）

- 更接近用户实际看到的文本

## LocatorAssertion类

```Shell
expect(popup).to_be_visible()    # 验证元素可见
*expect(locator).to_contain_text(\"substring\")    # 验证文本内容*
```

> 同类方法比较，主要区别在于它们对元素存在性和可见性的检查：
> 
> 

|方法|检查元素存在DOM|检查元素可见|
|---|---|---|
|`to_be_attached()`|是|否|
|`to_be_visible()`|是|是|
|`to_be_hidden()`|是|是（但必须隐藏）|
|`not_to_be_visible()`|否|是（必须不可见）|

选择使用哪个方法取决于你的测试需求：

如果只关心元素是否存在于DOM中，使用 to\_be\_attached\(\)

如果关心元素是否可见，使用 to\_be\_visible\(\) 或 not\_to\_be\_visible\(\)

如果确认元素存在但应该被隐藏，使用 to\_be\_hidden\(\)

# wait\_for\_load\_state方法

## **`load`**** 和 ****`domcontentloaded`**



**`wait_for_load_state("domcontentloaded")`**** **

含义：等待页面的 `DOMContentLoaded` 事件触发，即 HTML 文档解析完成，DOM 树构建完毕，但不必等待样式表、图片、子框架等外部资源加载完成。

应用场景：

- 只需要操作 DOM 元素（点击按钮、填写表单），不关心图片等资源是否加载完

- 希望尽早开始交互，提升测试执行速度

- 页面有大量图片但操作不依赖图片时

- 例如：一个登录页面，只需要定位用户名/密码输入框并填写，无需等待背景图片加载完



**`wait_for_load_state("load")`**** **

含义：等待页面的 `load` 事件触发，即整个页面及其所有依赖资源（图片、样式表、脚本、iframe 等）全部加载完毕。

应用场景：

- 页面包含大量图片、字体、第三方脚本等静态资源，需要确保它们全部就绪后再操作

- 需要截图且要求图片完整渲染时

- 页面逻辑依赖外部 CSS/JS 文件加载完成后才可交互的场景

- 例如：打开一个数据报表页面，里面的图表依赖外部 JS 库和图片资源，必须等 `load` 才能保证图表渲染完成



根据具体场景选择其一：

- 如果需要确保一切资源就绪 → 只用 `"load"`

- 如果只需要 DOM 就绪即可操作 → 只用 `"domcontentloaded"`



## 无法覆盖的场景

**`load`**** 和 ****`domcontentloaded`**** 只在页面首次加载时触发**

这两个事件是页面级别的生命周期事件，只有在浏览器加载一个新页面（或刷新）时才会触发。

如果前端项目是一个 Vue\.js \+ Element UI 的单页应用（SPA），大部分操作都只是局部 AJAX 更新，根本不会触发这两个事件。

### AJAX 局部更新（最常见）

点击按钮后触发 API 请求，前端局部更新 DOM，不会重新触发 `load` / `domcontentloaded`：

```Python
self.click_action(name, "修改规格")
            self.wait_for_page_ready()
```

这里点击"修改规格"后，对话框内容是通过 AJAX 加载的，`wait_for_page_ready()` 中的两行等不到任何新事件，几乎相当于空操作。

### 下拉菜单选项加载

选择下拉选项后，选项列表是异步加载的，DOM 事件不会重新触发：

```Python
self.page.locator("form div").filter(has_text="物理机").get_by_placeholder("请选择").click()
        self.page.wait_for_timeout(3000)
```

这里只能靠硬等 3 秒，因为 `load` / `domcontentloaded` 不会因下拉展开而触发。

### 搜索结果刷新

搜索是典型的 AJAX 操作，返回后只更新表格区域：

```Python
self._btn_search.click()
            self.wait_for_page_ready()
            self.page.wait_for_timeout(1000)    *# 等待1秒，确保搜索结果加载完成，解决搜索用例断言不稳定的问题*
```

注释已经说明了一切——`wait_for_page_ready()` 不够用，必须额外 `wait_for_timeout(1000)` 来弥补。

### 对话框内异步加载内容

打开对话框后，对话框内容可能还在通过 API 加载：

```Python
*# 等待挂载CD-ROM对话框出现*
        self.wait_for_page_ready()
```

对话框出现 ≠ 内容加载完成，`load` 事件不覆盖对话框内的异步渲染。

### Element UI Loading 遮罩

你们已经意识到了这个问题，所以加了 `.el-loading-spinner` 的等待：

```Python
loading_spinners = self.page.locator(".el-loading-spinner")
        count = loading_spinners.count()
        if count > 0:
            for i in range(count):
                loading_spinners.nth(i).wait_for(state='hidden')
```

但这部分其实才是真正有效的等待，前面两行 `wait_for_load_state` 在 SPA 场景下基本无效。

### 树形控件展开/折叠

```Python
tree_item.locator(".el-tree-node__content").first.click(force=True)
            self.page.wait_for_timeout(500)
```

树节点的展开是纯前端异步渲染，只能靠硬等。

## 应对方法

### 第一层：依赖 Playwright 的 Auto\-waiting（首选）

python

```Python
*# 大多数情况下，直接操作即可，Playwright 会自动等待元素可交互*self.get_by_text("确定").click()
self.get_by_placeholder("请输入名称").fill("test")
```

### 第二层：等待特定元素出现/消失（针对性强）

python

```Python
*# 等待 loading 遮罩消失（你们已经在用了）*self.page.locator(".el-loading-spinner").wait_for(state="hidden")

*# 等待表格数据出现*self.page.locator(".el-table__body-wrapper .el-table__row").first.wait_for()

*# 等待对话框出现*self.page.locator(".el-dialog:visible").wait_for()
```

### 第三层：等待特定 API 请求完成（最精准）

python

```Python
*# 等待特定接口返回后再操作*with self.page.expect_response("**/api/ecs/list") as response_info:
    self._btn_search.click()
response = response_info.value
*# 此时接口已返回，数据一定已就绪*
```

### 第四层：`networkidle` 只作为最后手段

python

```Python
*# 仅在无法定位具体元素或接口时使用，且设置合理超时*self.page.wait_for_load_state("networkidle", timeout=10000)
```
